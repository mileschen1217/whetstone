# Request — 三張要簽的頁面分成兩層（草稿，由 owner 的原話拼成；owner 改過才算數）

whetstone 跑完第一個真實專案的 epic（兩個 unit）之後，我發現 epic.md、brief.md、pr.md 把每一件被固定的事（決定、AC、finding、memory 句子）以同等地位列出，我看不出哪些需要我判斷。brief 我不知從何 review 起，AC 多是設計實作，我不確定自己能不能 review；decision 加上脈絡變得很長；ship 時我不太懂需要我簽 pr.md 的目的是什麼。兩個 unit 的 merge 決定我都是從對話摘要做的，不是從頁面。

我要的是：每一頁自己分出「需要 owner」與「紀錄」兩層，不刪任何東西。線的判準不要另外發明：第一題用 ship 已經在寫的三個 follow-up 標籤（無聲、留下 diff 之外的狀態、有 diff 之外的讀者，也就是錯了能不能復原、復原的 effort、爆炸半徑）；第二題是「定的是 owner 的事，不是 builder 的事」，列舉四種算 owner 的：一個數字或門檻；一個使用者看得到的名字或訊息；範圍的界線（什麼在內、什麼在外）；某樣東西不在或失敗時怎麼辦。模組怎麼切、檔案內部格式、演算法是 builder 的。這份清單對不對，intent 時問我。

同一件事的另外三個部件，這個 epic 一起做：brief 的每條決定標「由 AC-n 承接」或明寫「沒有 check」；brief 簽名前由一位沒寫它的讀者做兩個有界的走訪（每條 AC 的 check 有沒有漏測或多測；每條決定與 REQ 有沒有一條會紅的 AC），只回報缺口；review 的 finding 修正之後，由一位沒寫修正的讀者對每個 finding 判 closed／open，只看修正動到的函式，一輪。

成功的樣子：拿真實專案 unit 1 的 brief 與 ship 頁改成分層後的版本，我只讀線上的部分就能做出接受／merge 的決定，並用自己的話說出理由。要避免：線畫錯（線下的決定後來出事）；為了分層讓頁面變長或多出解釋；「需要 owner」那段變成空的形式。「每頁一個走過一遍的範例」這次先不做。

簽名前由獨立讀者查 AC，以及修正後的 burn-down，都先量再接：每份 brief 多一次派工，目前只有一次找到缺口的證據。

這是 whetstone 第一次用在自己身上。第一個 unit 的量尺「owner 只讀線上部分就能決定並說出理由」不是本機可執行的 check；brief 的 AC 表有 `Where: live` 這一欄，證據檔可以是我讀完頁面後寫下的決定與理由。brief 自己有沒有想到這一點，也記下來。
